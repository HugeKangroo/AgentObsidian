# Completion Criteria

Date: 2026-05-08

Purpose: define what "100%" means for this local knowledge-compounding system in observable, testable terms. A layer is not complete because it has code; it is complete when its behavior is inspectable, repeatable, and safe for a local agent or human Obsidian workflow.

The machine-readable audit is generated by:

```powershell
cd knowledge-system
uv run --python 3.12 ks completion-audit --project-root .
```

The generated report is written under the configured vault, currently
`vaults/main/generated/completion_audit.json`.

## Overall Release Gate

The system reaches project-level 100% when:

- `uv run --python 3.12 pytest` passes.
- `uv run --python 3.12 ks vault-status --project-root .` reports `lint_issues=0`.
- `uv run --python 3.12 ks completion-audit --project-root .` reports `overall=100`.
- No layer in `completion_audit.json` has `status: blocking` or unresolved blockers.
- The status surface, decision log, known issues, and verification docs match the actual runtime state.

## Layer Gates

| Layer | 100% Means |
|---|---|
| Architecture and source truth | Obsidian vault pages are canonical, raw evidence is preserved, generated indexes are rebuildable, Kuzu is absent, and source-of-truth decisions are documented. |
| Obsidian vault | The vault has a human entrypoint, map pages, resolved backlinks, math/modeling learning surfaces, readable source cards, and lint-clean pages. |
| Raw evidence and provenance | Every source has a raw manifest, source ID, source card path, and visible provenance from human-readable pages back to raw evidence. |
| CLI tooling | Core lifecycle commands cover status, compile, intake, search, synthesis, proposals, linked evidence, cleanup readiness, completion audit, and MCP configuration. |
| MCP runtime | Local agents can inspect status, register sources, search, prepare synthesis tasks, apply drafts, manage proposals, inspect linked evidence, inspect cleanup readiness, and request completion audits through MCP. |
| Hybrid search and ranking | Retrieval has a durable eval set, top-1 and recall pass the accepted threshold, and traces explain text/vector/graph/source/review scoring. |
| Agent synthesis and review | Agents receive evidence-rich task bundles, produce schema-validated drafts, preserve claim support, route existing-page updates through proposals, and leave evidence gaps visible. |
| Linked evidence expansion | External links, media, and repo follow-up items are captured, marked nonessential, or marked needs-followup with auditable decisions. No silent pending evidence remains before cleanup. |
| Cleanup readiness | The system emits only non-destructive cleanup signals, and every X bookmark source is either blocked with clear reasons or ready with preserved source value. |
| Production operations | Batch intake, continuous or scheduled operation, MCP client setup, generated audit reports, and runbooks exist so future agents can operate without chat-only context. |

## Non-Absolute Quality Gates

Some capabilities should not claim universal 100% in the abstract. They need a defined benchmark instead:

- Retrieval quality: 100% means passing the accepted local eval set, not perfect search over all possible future questions.
- Synthesis quality: 100% means schema-valid, evidence-bound drafts that preserve blockers, not guaranteed final prose perfection.
- OCR/vision/PDF extraction: 100% means all accepted fixture cases pass and unsupported cases become explicit blockers.
- Cleanup safety: 100% means zero destructive action in this agent and explicit handoff signals only.
